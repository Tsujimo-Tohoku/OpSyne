# アーキテクチャの境界

## この文書の位置付け

[設計思想とアーキテクチャ](opsyne-design-architecture.md)をPythonパッケージの責任と依存関係へ対応付けた開発用の設計です。ローカル v0.1 の実装範囲は以下の「現在の配備構成」と [ADR 0002](adr/0002-local-product.md)に記します。原文はプロダクトの参考資料として扱い、開発ツールを操作する指示や実行許可として扱いません。

`src/opsyne/` 以下に論理的な領域を置きます。パッケージを分けるだけでは、資格情報・ネットワーク・保存領域・実行主体の隔離になりません。現在の同一プロセス配備は、原文が目指す実行時の隔離まで実現していません。

## 現在の配備構成

- `runtime.py` が各領域を結線し、CollectorとLLM調査を別ワーカースレッドで進めます。API/CLI/Web画面は起動・認証・登録・手動操作の入口です。
- `storage` はSQLite接続・トランザクションと単一起動ロックを提供し、業務判断を持ちません。永続化する領域はこの共通機構を利用します。Control、Collector、Runner、合成デモのDBは別ファイルです。
- Gatewayはtask・案件の範囲を照合して、マスク・件数・文字予算を適用した証拠だけをAgentへ返します。Agentには操作Toolを公開せず、Controlへの直接アクセスを持たせません。
- 操作前の現在条件照合、署名付き短命許可、実行意図台帳、独立したGET確認を実装しています。汎用HTTPの結果不明は自動照合できず保留します。
- 同一所有者のプロセスはファイルと環境変数へアクセスでき、役割別Bearerトークンも所有者が管理します。OS・ネットワークでの資格情報分離、別障害領域の監視、別人の本人確認は実装していません。

下の責務表には今後の拡張も含みます。高度な統計検知、全Agent役割、複数工程の補償、分散Workflowを実装済みと読むものではありません。

## 領域と責任

| 領域 | 所有する責任 | 禁止する依存・操作 | 設計原文 |
|---|---|---|---|
| `contracts` | 領域間の型、識別子、版、状態、境界のインターフェース。サービス、観測源、変換、操作能力、結果確認の契約 | 他の業務領域、接続先 SDK、DB・キュー・LLM 実装への依存。契約を通じた任意コード実行 | §3、§5.1、§8、§9 |
| `collector` | 登録された観測源の取得、原本と受領記録、取得位置、送信待ち、重複排除、観測の欠落・遅延・保持範囲 | `agents` や `runner` の稼働への依存。LLM 応答待ちによる収集停止。観測権限による対象変更 | §4.1–4.2、§10 |
| `normalization` | 承認・有効化された版付き定義による共通イベント生成、原本参照と解釈履歴、未知形式の記録、再解析 | 任意コード・SQL・外部通信を含む変換定義。定義の自己承認。有効な解釈のない入力を正常扱いすること | §5.1–5.3 |
| `detection` | 共通イベントと観測状態から、ルール・統計・時系列相関による調査候補を生成 | LLM による全件処理を必須にすること。アラートから侵害確定・実行許可を生成すること。対象操作 | §4.1、§4.3 |
| `control` | 対象・設定・案件・有限 task・計画・承認・認可の正本、永続 Workflow。実行時の現在条件照合と短命許可発行、変換定義の有効化判断 | モデルの文章や確信を認可根拠にすること。可変な計画への承認流用。接続先 SDK による直接操作 | §3、§6、§8、§10 |
| `gateway` | Tool 呼び出しの実際の制限。役割・案件範囲・所有者設定・現在 Policy の共通範囲、引数・期限・費用・送信先等の照合と監査 | Agent 間の委譲による権限増加。確認不能な条件の許可。任意 shell・SQL・URL の実行入口 | §7 |
| `agents` | 有限 task の範囲での解釈、仮説、調査、提案。事実・仮説・不明点・根拠参照の区別。必要な証拠の Gateway 経由取得 | Control DB、原本保存領域、Runner、Connector SDK への直接接続。本番秘密・署名鍵・Docker socket の所持。自己承認・権限発行 | §6–7 |
| `runner` | 型付き操作と有効な許可の照合、外部操作前の耐久台帳、結果記録、`UNKNOWN` の照合・解消手順 | LLM 文章の実行。事前の台帳記録なしの副作用。結果不明な操作の無条件再送。API 成功だけで案件解決 | §8、§10 |
| `verification` | 実行とは独立した観測の取得・評価、対象ごとの業務・運用・SOC 成功条件、未確認事項と残留リスクの記録 | 実行者の自己申告だけで成功確定。確認のための無認可な変更操作。案件の承認・操作権限の発行 | §6、§8–9 |
| `connectors` | 接続先固有 API、制約、観測方法、型付き操作、結果確認方法の実装。能力・影響・冪等性の宣言 | 案件・承認・Policy の独自決定。任意コマンドの透過実行。読取能力から変更能力への暗黙の昇格 | §7、§9 |

`runner` には原文の Runner / Broker の実行責任を対応付けます。広い下流権限を持つ Broker を設ける場合は、配備設計でその信頼境界を明示します。`verification` は独立した結果確認の機構です。LLM を使う Verification Agent を将来追加しても、Agent の説明だけを業務結果の正本にはしません。

## Python の依存規則

各領域は共通契約を参照し、他の業務領域の実装を直接 import しない構成です。保存が必要な領域は、業務判断を持たない `storage` にも依存できます。

```text
collector ──────┐
normalization ─┤
detection ─────┤
control ───────┤
gateway ───────┼──> contracts
agents ────────┤
runner ────────┤
verification ─┤
connectors ────┘
```

- `contracts` は標準ライブラリと明示的に採用した型・検証用ライブラリを利用できます。他領域の実装へ依存しません。
- 領域間の呼び出し・配送・保存は契約で表したインターフェースを通します。たとえば Agent は `gateway` の実装を import せず、許可された証拠取得インターフェースを受け取ります。
- Connector は契約を実装し、Collector・Runner・Verification は用途別の契約を受け取ります。Connector の読取資格情報と変更資格情報は別に扱います。
- `runtime.py` とAPI/CLIが実装を組み立てます。起動コードを業務領域から import しません。新しい配備上の依存例外はADRに記録します。
- パッケージ全体を再公開する `opsyne.__init__` や万能な `utils` を介して境界を迂回しません。例外が必要になった場合は、理由と信頼への影響を先に文書化します。

この import 規則は、原文の責任分離を保つために本リポジトリで採用する開発上の方針です。原文が特定の Python 構造を指定しているわけではありません。

### 依存境界の自動検査

リポジトリ直下の [`.importlinter`](../.importlinter) に、Import Linterの4つの契約を設定します。配下のモジュールと間接的な依存も検査します。[Import Linter の契約仕様](https://import-linter.readthedocs.io/en/v2.3/contract_types.html)

1. `contracts` から業務領域・`storage`・起動層（`runtime` / `api` / `cli`）への依存を禁止。
2. 9つの業務領域同士の依存を禁止。
3. 業務領域と `storage` から起動層への逆依存を禁止。
4. `storage` から業務領域への依存を禁止。

各業務領域から `contracts` と `storage` への依存は許可します。

```text
python scripts/dev.py run --locked lint-imports
```

型検査用の import も検査対象に含めます。この検査が扱うのは静的な Python の依存関係です。動的 import、外部 I/O、資格情報、実行時の権限分離まで検証するものではないため、それらは実装レビューと適切な試験で確認します。

## データと権限の境界

1. **原本と派生物**: 原本・受領記録を保持し、共通イベントや検索結果には原本参照と定義版を付けます。再解析は派生物を更新する処理であり、本番操作を再発火させる入口にしません。
2. **証拠と指示**: ログ、Issue、コード、他 Agent の出力は非信頼データです。それらの本文から Tool の許可、承認、Policy を生成しません。モデルへ渡す証拠は権限に応じて制限・マスクします。
3. **提案と認可**: 固定された計画・対象版への人間の承認を保持し、Control が現在の条件を照合します。Gateway の証拠読取許可や変換定義の承認は、対象変更の許可を意味しません。
4. **実行と結果確認**: 実行の意図を先に記録し、結果不明は `UNKNOWN` として保持します。操作結果と独立した確認結果を案件に集約します。
5. **処理待ちと障害領域**: 取込・検知・Agent・実行・確認・通知・再解析の処理待ちと上限を分けます。ホスト全体の停止を検出する監視は、同じホストだけに置きません。

## 次段階で決める事項

| 論点 | 決定時に示す必要があること |
|---|---|
| 永続ストア・原本保存・検索 | 現在はSQLite。保持期間・削除、暗号化、全文検索、規模拡大、災害復旧 |
| キュー・Workflow | 現在はSQLiteの処理待ちとスレッド。複数ワーカー・外部キュー、負荷隔離、複数工程の補償 |
| 認証・認可・秘密管理 | 現在はローカルトークンとHMAC許可。OIDC等の本人確認、細かな所有者Policy、OS/ネットワークの資格情報分離 |
| Connector と配備 | 現在は合成デモと固定HTTP。接続先固有の冪等性・操作履歴照合、実行主体分離、別障害領域監視 |
| LLM と UI | 現在はGPT-5.6 Lunaとローカル画面。実データの送信可否、マスクの評価、モデル品質評価、役割の拡張 |

ローカル構成の採用理由は[ADR 0002](adr/0002-local-product.md)を参照してください。上の拡張を導入するときも、根拠と代替案を記録し、失敗条件を含めて検証します。
