# 開発の段階計画

## 目的と現在地

[設計思想とアーキテクチャ](opsyne-design-architecture.md)を実装へ進めるための計画です。Python 3.12 + uvに加え、ローカル v0.1 としてSQLite、FastAPI/Uvicorn、同梱Web画面、OpenAI APIの `gpt-5.6-luna` を採用しました。[ADR 0002](adr/0002-local-product.md)に判断を記録しています。

開発基盤の整備後、下表の範囲を実装しました。以下の各段階は、原文に対応する広い成果物・受入条件を引き続き保持しています。ローカル実装と試験の成功だけで、各段階全体や本番適合が完了したとは扱いません。

原文はプロダクトの参考資料であり、開発者や Agent が外部サービスを操作する許可ではありません。領域の責任と依存は[アーキテクチャの境界](architecture-boundaries.md)に従います。

### ローカル v0.1 の実装状況

| 段階 | 実装した範囲 | 残る主な範囲 |
|---|---|---|
| 1 契約・観測 | 型、SQLite原本・送信待ち、push/ファイル取込、重複排除、取得位置、欠落・遅延・解析状態 | 保持期限・削除、外部観測源の全履歴回収、規模検証 |
| 2 共通化・案件 | 宣言的JSON変換、対象版と定義版、未知・曖昧性、再解析、ルール検知、永続案件 | 統計・時系列相関、非JSON構文の共通化、高度な探索 |
| 3 承認・認可 | 固定計画と別主体承認、短命署名許可、世代失効、証拠Gateway | 組織の本人確認、細かなPolicy、配備上の秘密分離 |
| 4 実行・検証 | 実行意図台帳、UNKNOWN保持、合成対象の照合、HTTP操作と独立GET確認、停止時バックアップ・復元保留 | 汎用HTTPの正本履歴照合、複数工程・補償、別障害領域監視 |
| 5 LLM | 範囲と予算を制限した調査、根拠検査、同形式ログからのAdapter Agent自動提案・標本検証・承認待ち、重複・再試行制御、合成データでのLuna実API E2E | 実データ評価、各専門役割の拡張 |
| 6 導入 | ローカルダッシュボード、トークン、対象・観測源・操作・確認の登録、デモ | 複数利用者向け認証、運用品質・負荷評価、開発/PR/配備連携 |

操作方法は[利用手順](usage.md)、失敗系を含む検査の実行方法は[開発手順](development.md)を参照してください。実LLM・実サービスの接続成功は、模擬HTTPの検査と分けて記録します。

## 進め方

- まず決定論的な契約と状態遷移を定義し、合成データと偽の接続先で失敗を再現します。
- 各段階では正常系だけでなく、未知・結果不明・重複・権限不足・停止からの再開を受入基準に含めます。
- 正本、観測、承認、操作の意味が固まる前に、LLM や画面を中心に実装を広げません。
- 未対応状態は明示して保持します。実装の都合で正常、ゼロ件、成功へ置き換えません。
- 選定や仕様追加は根拠と代替案を記録します。各段階の完了は、対応する試験と成果物をレビューして判断します。

## 段階 1: 契約・状態遷移・原本・観測完全性

**設計対応:** §2、§3、§4.1–4.2、§5.1、§9、§10

### 成果物

- サービス、観測源、原本参照、受領記録、共通イベント、観測状態の型と検証規則。
- 案件、計画、承認、実行許可、操作結果、独立確認結果の最小契約。操作結果の `UNKNOWN` と、解析不能・観測不足の区別。
- 各状態の遷移表。遷移の主体、前提条件、永続化する内容、拒否時の結果を明記。
- 最初の偽 Connector と Collector の縦断処理。登録された観測源の範囲、取得位置、送信待ち、受領確定を扱う。
- 正本と派生データの保存方針、重複排除の識別規則、障害注入用のテストデータ。

### 受入基準

- 送信前・保存後・受領応答前・取得位置更新前後で停止させても、再開時に原本を失わず、送信待ちを未確定のまま消さない。
- 同じイベントを再送しても、規則で定めた同一イベントの派生処理や案件化を重複させない。異なるイベントを過剰に同一視しない。
- 最終受信、処理遅延、取得位置、欠落区間、解析失敗、保持範囲を個別に確認できる。観測源停止・権限不足・未取得期間を正常やゼロ件にしない。
- 原本と受領記録を保持し、解析失敗後にも原本へたどれる。ログにない時刻・主体・結果などを事実として補完しない。
- LLM や Runner が停止していても Collector を動かせる。製品用の変更資格情報を必要としない。
- 状態の不正な遷移や必須情報の欠落を拒否する。認可条件が不明な場合は許可を発行できない。

## 段階 2: 決定論的な共通化・検知と案件管理

**設計対応:** §4.3、§5.1–5.3、§6、§9–10

### 成果物

- 限定された宣言的な変換定義、その版・対象実体・エンジン・適用条件・根拠の管理。
- 構造、適用範囲、不正入力、競合を検査する仕組みと、人間が確認した版を有効化する経路。
- 共通イベントと原本の対応、使用定義の版、未知形式・意味不明値の記録。
- 既知ルール・観測停止・未知形式増加などから案件へつなぐ最小経路。根拠参照と有限 task の永続化。
- 新規取込と再解析を分けた処理待ち。最初の検知方式の選定理由。

### 受入基準

- 未対応値、型の変化、適用条件外、複数定義への一致は未知として残る。構文を解析できても意味不明な結果コードを成功にしない。
- 任意コード・SQL・外部通信を含む変換定義を拒否する。定義の承認が対象操作の権限にならない。
- 定義や対象版の変更後に古い承認を流用できない。定義の失効や再解析で原本を変更せず、有効な解釈を判別できる。
- 同じ入力の再解析や再配送で、本番操作を再発火させない。案件と証拠の関連付けを復元できる。
- 検知がないことを安全の証明としない。観測不足や未対応形式を調査の入口にできる。

## 段階 3: 計画・承認・認可と Gateway

**設計対応:** §2–3、§6–8、§10

### 成果物

- 対象、操作順序、根拠、事前条件、影響、成功条件、中止条件、復旧・補償条件を持つ計画契約。
- 固定した計画と対象版への承認記録、Control の現在条件照合、限定された短命許可。
- Gateway の呼び出し検査、主体・役割・task・対象・Policy の照合と監査。
- 権限不足を明示する結果、期限切れ・失効・競合の処理、承認と認可の状態遷移。

### 受入基準

- 役割、案件範囲、所有者設定、現在 Policy のどれかが拒否すれば呼び出しを拒否する。確認できない条件も拒否する。
- 提案者の自己承認、委譲による権限増加、ログ本文の「承認済み」、モデルの確信から許可を生成できない。
- 承認後の計画変更、対象置換、期限切れ、Policy 変更、競合、事前条件不成立を実行前に検出する。
- 読取許可から変更許可を導かない。必要範囲外の証拠取得は、不足として案件に残す。
- 再起動しても案件・計画・承認・認可理由が会話履歴に依存せず復元できる。

## 段階 4: 実行台帳・結果不明の照合・独立検証

**設計対応:** §7–10

### 成果物

- 最初の偽の型付き操作能力、Runner の許可照合、操作前の耐久台帳。
- 冪等性、外部操作履歴、対象実状態を用いた照合の契約。自動照合不能時の引き継ぎ経路。
- 実行から独立した業務・運用・SOC の結果確認と残留リスク記録。
- 復元手順、別障害領域からの監視方針、実接続前の資格情報・ネットワーク・実行主体の配備設計。

### 受入基準

- 外部副作用の前に意図を永続化する。許可不正、期限切れ、台帳記録失敗時は操作しない。
- 操作受理直後のタイムアウトや Runner 停止を `UNKNOWN` として残し、無条件に同じ操作を再送しない。照合できるまで次の危険な工程へ進まない。
- 重複配送と復元後の再開で、操作が二重実行されないことを接続先の能力に即して検証する。照合・冪等性を保証できない接続先では自動再実行を禁止する。
- API 成功応答、プロセス起動、HTTP 応答、業務復旧、侵害影響の除去を別の結果として記録する。確認不能なら未解決の状態を保持する。
- 補償操作にも許可が必要となる。複数工程の失敗時に、どこまで作用したかを復元できる。
- DB・実行台帳・送信待ち・取得位置・鍵・認可世代の照合を含む復元試験で、復元前の操作を忘れて再実行しない。

## 段階 5: LLM による調査・提案

**設計対応:** §2、§5.2、§6–7、§9–10

### 成果物

- 最小の Agent 役割から始める有限 task と、Gateway 経由の証拠取得。
- 事実、仮説、不明点、根拠参照、提案を区別する構造化出力。
- マスク済み標本からの変換案と、対応計画の提案経路。既存の機械検査・承認・認可を利用する。
- モデル送信先、データ分類、費用・時間・件数上限、停止・拒否・不正出力時の評価方法。

### 受入基準

- ログ、Issue、コード、他 Agent の出力に命令を混ぜても権限が変わらず、秘密や許可範囲外のデータへアクセスできない。
- Agent に本番秘密、署名鍵、Control DB 直接接続、任意 shell・SQL・URL 経路を渡さない。
- 根拠不足や意味不明な入力は提案保留・追加情報不足として返せる。モデルの出力だけで変換を有効化したり操作を認可したりしない。
- モデル停止、費用上限、不正出力があっても収集を継続し、案件と処理待ちを失わない。
- Adapter、SRE、Security 等の役割を追加するたびに、その役割の証拠範囲と拒否条件を評価する。役割数を品質の証拠にしない。

## 段階 6: 導入体験と実サービスへの段階展開

**設計対応:** §1、§6、§8–10

### 成果物と判定

- 対象・観測源・所有者・必要権限・業務成功条件を登録する導入経路と、版が固定された計画を確認できる承認 UI。
- 最初の実 Connector を、観測・提案・限定操作の順に追加する。対象・期間・操作能力を定め、前段階の拒否・失敗・復元試験を実接続に対して確認する。
- 監査、保持、マスク、費用上限、別障害領域での監視、復旧手順の運用確認。
- 開発連携が必要な場合に、案件から再現、隔離修正、PR、独立 CI、承認、配備、独立確認までをつなぐ。成果物の版と digest を計画に結び付ける。

本番接続・操作の開始は、この文書による一括許可ではありません。登録された対象、接続先権限、製品内の承認・認可、および実際の作業依頼の範囲で進めます。

## 採用済み構成と次の技術判断

| 決めるもの | 決定する段階 | 主な判断材料 |
|---|---|---|
| Python の対応版の更新方針 | 更新が必要になった時点 | 現在は Python 3.12 を採用済み。CI と開発 OS、依存ライブラリ、再現性を確認する。実際の設定は `pyproject.toml` 等を正とする |
| DB、原本ストレージ、検索 | SQLite採用済み | イベント量、保持・削除、暗号化、検索・復元の規模評価 |
| キュー、Workflow 実装 | SQLiteの待機状態＋同一プロセスのワーカー | 外部キュー、負荷隔離、複数工程・複数ホストの停止・再開 |
| 宣言的な変換の表現 | JSONのdot path・条件・値mapを採用済み | 非JSON、意味の評価、接続先ごとの適用範囲 |
| 認証、Policy、秘密管理、署名 | ローカルトークン・HMAC・世代失効を採用済み | 本人確認、所有者Policy、実行主体と接続先の権限分離 |
| 最初の接続先と配備単位 | 合成デモ・HTTP、単一ホスト | 接続先固有の履歴照合、冪等性、独立検証、実行時隔離 |
| LLM、SDK、モデル評価 | OpenAI SDK・GPT-5.6 Luna採用済み | 実データの送信可否、根拠の品質、費用・マスク評価 |
| API、UI、認証体験 | FastAPI/Uvicorn・同梱Web画面を採用済み | 複数利用者の認証、運用での承認・復旧体験 |

依存ライブラリは、必要になる段階で理由を記録して追加します。将来使う可能性だけを理由に、実行系・LLM 系・UI 系の依存を初期環境へまとめて導入しません。
