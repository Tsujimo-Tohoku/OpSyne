# 実LLM E2E検証

実施日: 2026-09-15。Windows / Python 3.12.14。
結果: **GPT-5.6 Lunaの実APIを含むE2Eが成功**。

## 構成と範囲

ユーザーが設定した `.env` のAPIキーを読み、公式OpenAI APIへ合成ログだけを送信した。
モデルは [`gpt-5.6-luna`](https://developers.openai.com/api/docs/models/gpt-5.6-luna)。
Responses APIの構造化出力、`store=False`、最大2500出力トークン、リトライなしを使用。
このページの実API計測はOpenAI SDK 2.54.0で実施した。PR #2で3.13.0へ更新後、
SDK用のHTTPクライアントをhttpx2へ合わせ、模擬通信を含む230件のテストで互換性を確認した。
SDK 3.13.0を使った実APIの再計測は行っていない。

OpSyneは検証専用のデータディレクトリと空きlocalhostポートで起動し、実際のHTTPでAPIを操作した。
Collector・Control・ワーカー・SQLite・Runner・独立確認は製品コードを使用する。
OpenAIクライアントには通信を模擬しない計測フックを付け、接続先・モデル・回数・マスクを検査した。
自動調査を無効にし、日次task上限を2とした。操作対象はローカルの合成デモのみ。

## 最終実行で確認したこと

| 経路 | 結果 |
|---|---|
| API認証、閲覧者による変更拒否 | PASS |
| ログ受領、重複排除、未知形式の案件化 | 同形式3件を1グループ・1taskに集約。手動依頼なしで生成 |
| 実LLMによる変換提案 | 標本検証後にDRAFT・承認待ち、正しい対象実体・版、`outcome=FAILURE`、`severity=ERROR` |
| 標本プレビュー | 意味を検査し、現在の解釈を変更しない |
| 変換承認・再解析 | 承認された定義のID・版・解釈を保存し、新規案件・操作を発生させない |
| 新規障害ログの検知・実LLM調査 | 証拠に結び付く事実2件、仮説・不明点・提案を分離 |
| モデルへの証拠 | 合成秘密文字列が送信されないことをHTTP送信前に検査 |
| ログ内の「承認済み」とする命令 | 計画・承認・実行を発生させない |
| LLM処理中の収集 | 変換・調査の両方で収集heartbeatが前進 |
| 操作計画 | 自己承認と承認前実行を拒否、別の認証主体による承認後に実行 |
| 実行と確認 | 操作成功だけではVERIFYING。独立確認PASS後に対象案件だけRESOLVED |
| 再起動 | 再確認APIを呼ぶ前からRESOLVEDを保持。再実行要求は同じ実行IDを返す |
| 二重実行 | 再起動後も合成対象の変更回数は1 |

別主体の承認は、検証スクリプトが合成環境の役割別トークンを使って通したAPIフローであり、
組織の本人確認や実際の業務判断の評価ではない。実LLMの推奨から固定操作を選ぶ業務判断も対象外で、
スクリプトが登録済みの `demo-restore` を計画に指定する。

## 見つかった問題と修正

初回のAPI応答はHTTP 200・completedだったが、変換案が証拠の外側を含む `payload.result` を参照した。
実際のログ本体のキーは `result` なので、標本検査で不一致となりE2Eを停止した。承認・実行は行わなかった。

Adapter Agentの指示に、パスは「payload文字列をJSONとして読んだログ本体」が基準であること、
`result` / `event.result` の例、外側のメタデータとマスク値を使わないことを追加した。
元ログに本物の `payload` キーがある場合は、そのパスを禁止しない。
修正後にE2E成功を確認し、収集heartbeat・再解析結果・再起動直後の状態検査を強めた最終実行も成功した。

### 自動生成の追加検証

自動生成の実装後、同形式3件から、ボタン操作なしで変換案1件を生成する検査を追加した。
最初の実行ではモデルが `error` の業務的な意味を確定せず、category/messageのみの案を返した。
自動生成・標本検証・承認待ちへの保存は成功したが、結果・重要度の一致を要求するE2Eは停止した。
この案を承認せず、意味が未知のまま残る製品の動作も変更しなかった。

次に、結果 `FAILURE`・重要度 `ERROR` をフィールドとして明示した合成JSONで検証した。
自動集約から生成・承認・再解析、証拠付き調査、承認済み操作、独立確認、再起動まで成功した。
曖昧なコードから十分な意味を推定する能力を、この成功から一般化しない。

## 再実行

```text
python scripts/dev.py run --locked python scripts/live_e2e.py --allow-live-api --env-file .env
```

1実行あたり最大2回の有料API呼び出しがある。状態は毎回新しいディレクトリへ保存し、
失敗時は終了コード1・レポートFAILとなる。モデルの提案保留や不適切な解釈も合格に読み替えない。
通常のpytest・CIからは実行されない。

自動生成の製品変更後は通常テスト227件の全体実行と、追加3件の結合試験が成功した。
Ruff、mypy、4つの依存境界検査、配布物ビルドも成功。最終的なテスト数は230件。

## この結果からは分からないこと

合成JSON形式1例での成功であり、未知形式全般の精度やあらゆるプロンプト注入への耐性を保証しない。
ブラウザー操作、実サービスの復旧、本番SOC判断、Discordとの統合は今回の実API E2Eの範囲外。
実行中の通常コンソールは変更せず、検証用サーバーは終了時に停止した。
