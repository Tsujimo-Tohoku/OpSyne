# ADR 0004: 変換定義に結び付いた監視目的と説明

- 状態: 採用（API接続形式のフロントエンド担当との確認は別途）
- 対象: [Issue #4](https://github.com/siro103/OpSyne/issues/4)

## 判断

承認画面が案件の最新の調査結果を参照すると、別の調査・定義の説明を表示し得る。
そのため説明は各変換定義のControlレコードに保存する。Agentの用途案・証拠付き根拠・
不明点は生成タスクの結果をスナップショットとして保存し、案件の説明から逆引きしない。
利用者の監視目的・把握したいこと・根拠・確認事項は別領域に保存する。
監視目的の欠落は未記録であり、Agentの用途案から補完しない。

定義の変換規則は従来どおり不変。未承認（DRAFT）の説明だけを楽観的排他制御で更新できる。
更新要求には現在のdigestを必須とし、同じDBトランザクション内で旧スナップショットを保存し、
説明の改訂番号を増やす。定義・説明・改訂番号・説明の編集者全員を新しいdigestに含める。
承認後と失効後の説明変更は拒否する。変更が必要なら新しいid/versionの定義として提案し直す。
既存の重複範囲チェックに従い、旧定義の失効と新定義の承認を行う。

説明編集者も提案者と同じく本人による承認を禁止する。別の人による再編集でも編集者の記録を
消さない。Agentの説明は人間向け編集APIでは書き換えられず、記録者は認証済みactorから決める。
説明は判断材料であり、実行権限や変換処理そのものには使わない。

## 互換性と保存

新規レコードは `review_schema_version=1`。既存の説明なしレコードは従来の定義digestで
読み出し・承認でき、一括書き換えはしない。初回の説明更新時に新契約へ移行する。
旧説明はControlの `adapter_review` オブジェクトに `定義id:説明改訂番号` をキーとして保存する。
レガシーの改訂番号は0として扱う。更新者と新digestは監査ログにも記録する。

API形式・表示時の欠落処理・エラーは [受け渡し仕様](../adapter-review-api.md) に定義する。
この変更はバックエンドと契約テストまでを対象とし、画面表示の接続はフロントエンド担当が行う。
