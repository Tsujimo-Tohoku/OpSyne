# ADR 0008: サービスを選択してから各機能へ進む画面構成

- 状態: 採用（ローカル v0.1）
- 関連: Issue #9、[ADR 0005](0005-service-scoped-queries.md)

## 背景

機能ごとの全体画面では、利用者が保守対象を画面ごとに確認する必要がある。
サービス別APIが返す正確な件数とページングを使い、対象と操作先を揃える。

## 決定

- 初回は `#services` のサービス一覧。サービス選択後は左側にホーム、インシデント、承認待ち、操作履歴、設定を置く。
- URLは `#services/{service_id}/{home|incidents|approvals|history|settings}`。詳細は `#services/{service_id}/incidents/{case_id}`。IDはURLエンコードする。
- サービス切り替えではトップレベルのメニューを維持し、詳細からは移動先のインシデント一覧へ戻る。不正URL・不存在・別サービスの詳細は案内し、他の対象へ補完しない。
- 件数はサービス別summary、インシデント・承認待ち・実行・履歴はサービス別itemsを使用する。全体overviewの上限付き一覧から集計しない。全件返す登録情報と共通設定は既存overviewを使用する。
- 一覧は50件ずつ読み、一部取得・取得済み0件・取得失敗を区別する。継続カーソルの409では蓄積したページを破棄して再取得する。続きを読み込んだ一覧は利用者の明示更新まで保持する。
- サービス遷移と認証切り替えで世代番号を変更する。以前の世代の応答は反映せず、確認画面を閉じ、承認→実行→復旧確認の後続要求を中止する。既に送った要求を取り消したことにはしない。
- 全体共通と所属不明の履歴には `#history/global` と `#history/unknown` の入口を設ける。AI・認証・復元管理の適用範囲は全サービス共通と明示する。

## 影響と制約

以前の `#overview`、`#cases` などサービスを特定しないURLは対象を推測せず、一覧への案内を表示する。
バックエンドAPI、永続化、認可契約は変更しない。サービス選択はアクセス権の境界ではなく、既存ロールの権限でAPIが判定する。

現在のsummaryにはサービス機能の最新正常性を表す契約がないため、一覧・ホームは機能の状態を未確認と表示する。ログ受信や案件0件から正常を推定しない。操作と独立確認の実測は実行記録に分けて表示する。
複数APIの取得は同一時点のスナップショットではない。操作時には既存サーバーが対象・版・期限・承認を再照合する。

ブラウザ終了後の処理継続、利用者によるUX評価、実サービス・実LLMの検証はこの変更の完了条件に含めない。Issue #9の利用者確認は別途記録する。
