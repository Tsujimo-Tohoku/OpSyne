# ADR 0005: サービス別の取得・件数・操作履歴

- 状態: 採用
- 対象: [Issue #6](https://github.com/siro103/OpSyne/issues/6)

## 背景

全体overviewを表示上限で切り詰めた後にサービスで絞ると、他サービスの記録に押し出された
案件・承認待ちを0件と誤認する。サービス別の履歴は、監査の文章やIDの見た目から推測できない。

## 決定

従来APIは維持し、サービス別サマリー・一覧と共通/所属不明履歴の読み取りAPIを追加する。
Control、Collector、Runnerの読み取りをcomposition層のServiceQueriesで組み合わせ、
サービスで絞った全件を集計してからページを切る。実行結果と独立確認結果は分けて返す。
ロールと自己承認規則に基づく `can_review` はレビュー主体の識別用であり、認可証にはしない。
変更系APIでは従来どおり対象・版・期限・状態・標本などを検査する。

ページカーソルは対象・主体・ロール・ページサイズ・全件のダイジェスト・位置を含み、
Controlの既存署名鍵で用途を分けてHMAC署名する。データが変わった継続要求は409にする。
変化した一覧を途中から継続して欠落や重複を隠すより、先頭から再取得を要求する。
取得が完了したか、1ページが全件を含むか、そもそも0件かをそれぞれ明示する。

新しい監査イベントは同一トランザクション内で `audit_scope` にサービス・対象種別・所属を
保存する。既知のイベント契約と構造化された対象から対応を確定し、本文は解析しない。
Runnerの実行・確認はRuntimeが明示的にサービスIDを渡す。
Collectorが保持する変更不可のsource/service対応を `source_scope` としてControlにも保存し、
変換定義の監査を結び付ける。起動時は登録済み観測源から対応を再構築する。

既存の監査には後から所属を付けず、`unknown` として返す。共通操作は既知のイベントのみ
`global` とし、どちらもサービス別履歴に混ぜない。サービス別履歴の `current_object` は
現在の対象を表示する補助情報で、記録時の状態を装わない。原本のactor/action/detailは不変。

## 制約

ローカルv0.1の全件読み取り方式であり、大規模な履歴に最適化したSQL集計・索引検索ではない。
ページ取得のたびに当該一覧を検査するため、更新頻度が高いと再取得が増える。
複数DBにまたがるサマリーは一括トランザクションではなく、取得時点付近の観測値。
サービス間の認可・テナント分離は導入しない。サービスIDは絞り込み条件であって権限ではない。
UIのサービス単位へのナビゲーション変更はこのAPIの利用側で行う。

契約と利用例は [サービスAPI](../service-api.md) を参照。
