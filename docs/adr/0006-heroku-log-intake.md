# ADR 0006: Heroku Cedarのログ受信と外部受信の明示設定

状態：採用（実装）。関連：#11。日付：2026-09-15。

## 問題

既存のファイルCollectorはVM内の読取に使え、一般push APIはOpSyne形式のJSONを受け取れる。一方、Heroku CedarのHTTPS Drainはバイト長付きLogplexを送るため、既存push APIへ直接接続できない。また既存CLIとHost制約はlocalhost限定だった。

導入の質問UIやGitHub接続とは独立に、外部ログを原本保存・解析・検知へ渡せる最小の入口が必要である。対象はCedarのみとし、Firや他社コネクター、初期化Agentの自動探索は含めない。

## 決定

### 接続先固有の変換

`connectors/heroku_logplex.py`でLogplexのバイト長・本文全体を検査し、各メッセージの原文バイトと、バージョン付きJSON投影を用意する。先に全メッセージと投影を検証し、不正フレームは保存しない。

JSON投影は`transport=heroku_logplex_v1`、原文のUTF-8表示`raw`、限定して読めたヘッダー`heroku`、本文`message`を持つ。本文が曖昧でないJSONオブジェクトなら`app`へ格納する。重複キー、非有限値、不正Unicode、非オブジェクト、過大な本文はアプリJSONとして解釈せず、元のテキストを残す。これは完全なRFC5424パーサーではなく、CedarのSTRUCTURED-DATAを省く形式に対応する限定した変換である。

ヘッダーの優先度や文字列ERRORだけから、業務上の成功・失敗を決めない。通常の承認済みAdapterが`app.level`等を解釈する。原文が不正UTF-8なら既存の`encoding_error`により解析はINVALIDになる。

### 原本と投影を区別する

要件書の「payloadにSyslog文字列のみを保存する」例では、JSONのみを扱う既存正規化へ接続できない。既存DBにある`original` BLOBと`payload`を使い分ける。

- `original` / APIの`raw_bytes_b64`：受信した個々のSyslogメッセージの正確なバイト列。
- `digest`：その原文バイトのSHA-256。
- `payload`：コネクターが作る解析用JSON投影。`raw`には原文の表示用テキストも残す。
- `encoding_error`：原文バイトのUTF-8妥当性。

Collectorの`ingest(..., originals=...)`だけを拡張し、既存のファイル取込が利用する原文保存処理へ渡す。一般push HTTP APIはこの追加引数を公開しない。既存RawInput/RawEvent契約・DBスキーマ・既存ログの意味は変更しない。コネクターに限ってpayloadが投影であることを利用手順に明記する。

原本の単位はLogplexフレーム全体ではなく、フレーム内の個々のメッセージである。フレーミングの長さprefix・HTTPヘッダーは原本BLOBに含めない。

### 再送と保存

`external_id=heroku:{frame_id}:{index}`と既存のsource単位の重複排除を利用する。比較は投影やUTF-8置換後の文字列ではなく原文バイトで行う。同じIDで異なる原文は409。同じ原文の再送では初回のイベントID・投影を返し、既存投影を上書きしない。

500件ずつ保存し、後半で停止した場合は再送で未保存分を補う。全リクエストの一括トランザクションは提供しない。成功の204は全チャンクの原本保存を意味し、解析や案件化の完了を意味しない。既存の永続pendingと観測ワーカーが後続処理を進める。

上流が同一フレームIDを同じ内容で再送する契約を前提とする。独立したフレーム台帳は追加しないため、フレームの件数だけが変更された再送の検出は提供しない。

### 認証と公開境界

専用`POST /api/drains/heroku/{source_id}`はHTTPSのみ。管理者がローカル設定ファイルでsource・service・Basicユーザーとパスワードの環境変数名を対応付ける。sourceごとに専用資格情報を用い、ユーザー名が異なっていても同じパスワードの使い回しを拒否する。sourceは既存の有効なpush sourceで、登録済みサービスとの対応が一致する必要がある。受信要求はsourceを新規作成しない。

Heroku Drain Tokenの環境変数名を指定した場合は、Basic認証に加えて一致を要求する。未指定でも必須ヘッダーとして形式検査するが、認証の根拠はBasic資格情報となる。所有者が明示した設定を起動時に読み、変更・失効の反映には再起動が必要。新規設定管理APIは作らない。

本文は宣言された長さと実際のストリームの両方で2,000,000バイトに制限する。件数・フレームID・ヘッダー重複・Content-Type等を検査する。通常のBearer認証、Origin制約、承認・実行制御は維持する。

待受IP・ポート・許可Host・信頼するプロキシIPを明示的に設定可能とする。既定はループバック。Hostのワイルドカードや全アドレスへのプロキシ信頼は拒否する。TLS終端、外部からのアクセス制御、接続時間・頻度・同時接続の制限は前段のプロキシ／ホスティングで設定する。外部公開は受信パスに絞り、管理UI/APIは私的な入口へ置く。アプリの同一プロセス構成は変えない。

監査にはsource、frame ID、件数、バイト数、結果、Drain TokenのSHA-256を記録し、Authorization・パスワード・Tokenの平文は記録しない。認証前やヘッダー検査段階の拒否は受信監査の対象外とし、前段のメタデータ監視で補う。

## 代替案

- 一般push APIへ直接送る：形式も認証も異なり利用できない。
- Syslog文字列のみをpayloadに入れる：原文は読めるが既存JSON解析につながらない。
- 正規化エンジンにHeroku固有処理を入れる：領域の責任が混ざるため採用しない。
- 新しい配送DB・専用ワーカーを作る：既存の原本・pending・重複排除を再利用できるため不要。

## 検証と制約

合成LogplexをASGI APIへ送り、原文保持、不正入力、資格情報の境界、再起動、途中失敗後の再送、承認済みAdapterによる検知・案件化を検証する。

実Heroku配送、公開TLS配備、実LLM、負荷・高可用性は本PRの検証範囲外。Logplexの完全配送も保証しない。ログの受信はサービス正常や自動復旧の準備完了を意味しない。
